# 一、方法（摘要）

任务 = 四码定长方案的同码候选重排：`argmax P(wᵢ | ctx)`，用交叉熵评分而非生成。

1. **分层并行解码**：所有候选共享同一段上文 → ctx 只解码一次，首 token 概率同帧计算；
   KV cache 复制到 M 个序列，N 候选 ≤ 3 次 `llama_decode`，与候选数无关
   （朴素法每候选独立 prefill 曾实测 274ms；现行延迟量级见 ②③——0.6B base ctx20/k6
   最坏情况 = 预填充 79ms + 候选段 100ms，前缀去重命中时更低）。
   边界：Qwen3.5 的 SSM 跨序列干扰要求每序列增量 1 token（准确率 98.5%；250+ 序列 batch 退化至 74%）；
   `llama_get_logits_ith` 的 i 是 batch 索引（误用致 ~40% 准确率）。
2. **预解码**：commit 后上文已定而候选未现，异步预解码 + KV 代次机制（`g_seq0_gen`）保证缓存一致性；
   完整评分流程成功后自我刷新预解码状态（修复连锁失配，曾占 30% 请求）。
   预解码命中时用户等待 = 候选段（miss 路径 = 预填充 + 候选段，见 ②③ 口径）。
3. **长词只解 3 token、无外推**（λ 尾部外推已证伪删除）：CE 位置权重 **(1.0, 1.10, 0.60)**
   加权前三 token（2026-11-14 随默认模型 0.5B 重标定，0.6B 沿用）；满长词组优先
   由 `two_code_sentence` 开关直接实现（2026-11-16），不依赖长度外推项。
4. **系统集成**：lua processor（上屏历史/预解码触发）+ lua filter（评分/缓存/AI 标记）+ C++ DLL，
   官方 rime.dll 零修改；`code_pattern` 正则全串匹配编码触发（默认 `.{4}` = 恰 4 码，2026-09-30 起取代 min/max_code_len 长度区间）；编辑键重置上文基座。
5. **训练语料收集**：上屏记「词+码」+ 真实候选窗快照（2026-08-02 起，替代字典反推）。

# 二、主要结论

## 核心结论（主线四步；①→②→③→④ 于 2026-11-18 定稿）

**统一口径**
- 输入 = 模型 × 上文 token 数（ctx）× 候选数 k（= 层1 词频排序后**进第 2 层 CE 融合窗的候选数**，即生产 `max_candidates`）。
- 输出 = **选重率**（错误率 = 1 − 首选正确率，越低越好）+ **CPU 中位延迟**。
- 延迟口径（2026-11-18 三次修正后**分段定稿**）：`SIM_PREP`（ctx 预填充）与
  `SIM_STEP23`（候选段两次 decode，预解码不计）**分开计时**；`SIM_TIMES` 保留整窗
  （prefill + 两次 decode + CE）作对照。**ctx 与 k 是两个独立预算**；命中路径的用户等待
  = 候选段，miss 路径 = 预填充 + 候选段。**最坏情况** = k 个候选全部 3 token、首 token
  两两不同（前缀去重失效）；空闲机器、睿频关 + 70% 上限；一个进程跑完该模型全部格。
  （只计"两次 decode"会把 ctx 的作用完全抹掉——ctx 成本全在预填充，见 ② 的口径教训。）
- 数据：wiki 多字词 **`cohort_big_60k` @3万 = 60,000 窗（主口径）**；融合参数每格各自最优
  （`eval/fusion_sweep_*.tsv`）。**展示口径 = 标定后的最优错误率**（每格 7350 组网格最优；
  同数据调参，split-half 估计的乐观偏差 0.03–0.04pp；不再展示留出/生产点列）。

**主线四步**：① 词频 → ② 上文预算 → ③ 候选预算 → ④ 精度/前沿。
模型文件固定为三个 official **base** 权重的自建 Q4_K_M：
**Qwen2.5-0.5B base**（397.8MB）、**Qwen3-0.6B base**（396.7MB）、
**Qwen3.5-0.8B base**（547.3MB）。量化与版本比较（base vs chat、Q4_K_M / Q4_0 /
Q5_0 / Q6_K）全部放**附录 A**，主线不再讨论量化配置。

结论（2026-11-19，6 万窗主口径）：**0.6B base 成为帕累托最优点
（k=6：候选 100ms / 最优误差 3.28%，预填充 79ms）**——比 0.5B base
（k=6：102ms / 3.56%，预填充 124ms）又快又准；0.8B base（k=4：91ms / 3.55%）
被 0.6B k5（84ms / 3.42%）支配；0.8B k6（135ms / 3.20%）是预算外精度前沿。
**同日生产已切 0.6B base + ctx=20/k=6**
（两版安装器/默认值/本机 schema 均已改；ModelScope 自建仓已上传，URL 已验证）。

### ① 用户词频：**衰减项 + 累计项**缺一不可

`cohort_big_full` @3万（205,966 窗，161 虚拟用户，无 CE 的纯词频口径）：

| 词频项 | 无（引擎序） | 只用衰减 | 只用累计 | **衰减 + 累计** |
|---|---|---|---|---|
| 选重率 | 13.65% | 8.25% | 8.21% | **7.86%** |

- 两项同时在场比只用任意一项 **−0.35~0.40pp**（大样本；20k 子集上 0.16pp）。
- τ 在纯词频口径**几乎不可辨识**（τ=50→800 全距 0.05pp，且 (τ,β) 退化：τ 小→β 大、误差不变）
  → τ 放到融合阶段联合标定（当前 400 仍在宽平台内）。
- 生产取 `fused = a_ce·L + b_dec·log1p(eff_τ) + b_cum·log1p(uni)`；联合扫参显示 b_cum 的平台在
  1.5–3.0（生产 1 略偏低，代价 ~0.1pp，见 ③ 的对照列）。

### ② 延迟第一段：T_prefill(ctx) —— 3 模型 × ctx 1–20（base Q4_K_M）

口径：整窗 **step1（ctx 预填充）段单独计时**（sim `SIM_PREP`，逐窗取中位；k 与预填充无关，
用 k=2），一个进程跑完该模型全部 ctx；空闲机器、睿频关 + 70% 上限。

### 附录 A：模型版本与量化（结论归档，2026-11-19）

> 现行主线只用三个 **official base 自建 Q4_K_M**（0.5B / 0.6B / 0.8B）；
> chat/对话版与全部量化变体文件已于 2026-11-19 清理。**本附录只保留结论**；
> 实验数值与逐变体记录见 `freq-fusion-research.md`（1 万窗小样本结果已从 README 移除）。

**A.1 结论一：base 优于对话微调版（chat）**

- 重排是纯文本续写似然，与预训练同分布、与对话微调异分布：对话版全窗 CE 均值
  系统性抬升，三代里 **0.6B 的差距最大**（对话版明显更差），0.5B 差距很小，
  0.8B 在融合后曾出现边缘反超（CE 更噪 → 词频修复空间更大），但不构成选 chat 的理由。
- 幅度 ∝ 后训练强度：Qwen3-0.6B 的深度思考后训练最重，对齐税最明显。
- **选型先固定 base，再谈量化。** 0.5B 的 base 版同时省 93MB（instruct 文件是非 tied
  转换，多一个 136MB 输出头）。

**A.2 结论二：Q4_K_M 是性价比最佳量化**

关键前提——**0.5B 做不了标准 Q4_K_M**：Q4_K 的 super-block = 256 元素，而
Qwen2.5-0.5B `hidden=896`（896 / 256 = 3.5，不整除）。`llama-quantize` 不报错，
但对 896 宽的张量静默回退，实际组成（`gguf_types.py` 实测）：

| 文件 | 张量组成 | 等效位宽 | 说明 |
|---|---|---|---|
| `05b_base_q4km`（397.8MB） | Q5_0 132 张 + Q8_0 13 张（含嵌入）+ Q4_K 12 + Q6_K 12 | ≈6.4 bpw | 只有 `ffn_down`（4864=19×256）是 K 量化 |
| `base06b_q4km`（396.7MB） | Q4_K 168 + Q6_K 29（含 tied 嵌入） | ≈5.3 bpw | 标准 Q4_K_M，零回退 |
| `base08b_q4km`（547.3MB） | Q4_K 132 + Q6_K 27（含 tied 嵌入） | ≈5.35 bpw | 标准 Q4_K_M，零回退 |

- 因此 0.5B 的“Q4_K_M”其实是 **Q5_0 体 + Q8_0 嵌入**（位宽比 0.6B/0.8B 还高）——
  它预填充慢是慢内核 + 8-bit 嵌入，不是参数量。
- **更低位不可取**：Q4_0 / Q4_0+out40 / 0.8B 嵌入 Q4_K（e4k）都掉精度
  （违背“正确率不能掉”）；**更高位不划算**：Q5_0 与 Q4_K_M 精度打平但预填充更慢，
  Q6_K / Q5_K_M 只变慢；0.8B 的 Q3_K_M/Q2_K 比 Q4_K **更慢**（低位 K 反量化开销）。
- **结论：Q4_K_M（→ 0.6B/0.8B 的标准 K 量化；0.5B 因块约束自动回退 Q5_0/Q8_0）
  是本任务延迟/精度曲线的甜点**；再压就掉精度，再加位只变慢。量化不改变 ctx\*=20。

**A.3 结论三：大模型出局（2B / 4B）**

2B（Qwen3.5-2B）**最低档位（k=2）候选段已 121.7ms，预填充 ctx20 260ms**，
已超出即时性要求；不做进一步选型实验。

4B（Qwen3-4B-Base base，自建 Q4_K_M 2.50GB，4.95 bpw）按用户 2026-11-19 指令
**只测能力上限**：同 6 万窗链 ctx20，k4/k5/k6 最优误差 **3.06% / 2.80% / 2.63%**
（同 k 比 0.6B 好 0.59–0.65pp）；但预填充 **462–472ms**、候选段 k2/k4/k6 =
**218 / 273 / 438ms**、整窗 k6 **916ms**，是 0.6B（79ms / 100ms）的 4–9 倍，
完全不可部署。结论：**规模收益仍单调（每 +3.4B 约 −0.6pp），但延迟代价 4 倍以上**，
在 110ms 预算内不存在可行点；不进入选型，仅作为“LLM 重排能力天花板”的记录。

- **0.5B/0.6B/0.8B 差距收敛到噪声级**（k6 诚实 1.56/1.56/1.60，互差 ≤0.04pp）——
  wiki 上 0.6B 对 0.5B 的 0.28pp 优势在用户域消失：**0.6B 在用户域无代价**。
- **4B 仍领先 0.10pp**（1.45 vs 1.56 诚实）但比 wiki（0.65pp）大幅收窄——
  域越易，能力上限的边际越小；仍 4–9× 延迟，不作部署。
- **生产参数迁移近乎无损**：0.6B 生产点 k6 = 1.60%，距该格 argmax +0.09pp。
  用户域 argmax 参数漂移（b_cum 顶格 2.0–2.5、w2/w3 偏高、τ 散）不采纳——
  27k 窗证据有限，生产参数维持 wiki 平台标定（两步法既定规则）；
  「用户域想要更强累计项」记为个性化方向的观察。
- 数据：`cohort_big_user/`（anchors/samples/streams + 四个 `ce_*_cuser_c20`）；
  扫参 `eval/fusion_sweep__base_models_c20_user.tsv`。

### LLM × 词频 2×2（0.6B base / ctx=20 / 生产点参数；2026-11-20 重测）

四格同窗同参（固定生产点 τ400 / w2 1.10 / w3 0.60 / b_dec 14 / b_cum 1.0；

| 域 | 无 LLM·无词频（引擎序） | 无 LLM·有词频 | 有 LLM·无词频（纯 CE） | 有 LLM·有词频（k6） |
|---|---|---|---|---|
| wiki 多字词 @3万（60,000 窗） | 17.98% | 10.27% | 4.75% | **3.29%** |
| 用户域 @3万（27,000 窗） | 12.62% | 5.43% | 2.98% | **1.60%** |

两个因子都有效且互补：wiki 17.98 →（词频）10.27 →（换成 LLM）4.75 →（两者）3.29。
词频把引擎序错误减半，LLM 在词频之上再减 2/3，两因子叠加优于任何单项；
k4/k5 → 3.67/3.44%（wiki）、1.76/1.66%（用户域）。
工具 `eval/calib/matrix_2x2.py`，报告 `eval/matrix_2x2_*.txt`。

> wiki 单字 35.48 / 9.16 / 7.95 / 5.05）为对话版时代历史口径，单字链已删不可复算；

### CSS 方法检验（2026-09-02，负结果，已放弃）

CSS（冲突语义相似度 = 码组候选对最大词向量余弦，曾用于"不跑 LLM 就估重排难易度"）经
13,000 条 4 码样本实测检验（修复侧 8,000 + 改错侧 5,000，部署口径 10tok/5cand）：
**代表性不足，放弃**——

- **可计算率仅 41%**：59% 样本窗内不足 2 个候选有词向量（腾讯 200d 词向量偏双字常用词）；
- 可计算子集内区分力弱：Spearman rho=-0.055 / AUC=0.570，修复率仅在最尾带（max_cos≥0.65，
  占全部样本 ~3%）明显下滑（81.7%→60%）；改错率方向正确（2.3%→11.1%）但基数太低；
- 同数据下词频比 AUC=0.678、目标-首选余弦 AUC=0.639 均显著更强（后者说明"难分"确实存在，
  只是该用目标对头名竞争者的相似度，而非候选对最大值——但静态码组指标无法知道目标词）。
- 相关过程文件已全部删除（2026-09-02）：检验脚本与报告、13k 原始数据（本库）、
  03处理脚本 eval_css.py、其固顶词候选输出（输出建议固顶词\，部署 pin_fix.txt 为用户手工
  维护、与其无关）、腾讯词向量缓存（~/.cache/wordvecs，116MB）。仅保留本节结论。

### 组句候选生成 + LLM 句级重排（2026-11-23，正结果；详见设计文档 §十一）

用外部 N-gram（万象 LTS gram，Rime octagram 格式）在万象词表上做词级 beam，生成
**5 个整句候选**；wiki A/B 两区各 100 句（3–12 词）的命中率：

| 模型 | N-gram top-5 A/B | 词表内 top-5 | LLM 整句 CE 重排 top-1 A/B | 词表内 top-1 |
|---|---|---|---|---|
| 万象 LTS（390MB） | **71% / 62%** | **82.9% / 84.5%** | **64% / 57%** | **73.7% / 81.0%** |
| Rime 官方八股文 bgw（206MB） | 67% / 53% | 82.9% / 72.4% | 62% / 49% | 76.3% / 69.0% |
| 千问内置剪枝版（10.4MB） | 54% / 46% | 65.8% / 63.8% | 50% / 43% | 60.5% / 62.1% |
| 微信 lmcnmac（16.8MB，已逆向） | 56% / 41% | 68.4% / 58.6% | 52% / 36% | — |
| 豆包 sys_bigram（48.6MB，已逆向） | 56% / 32% | 69.7% / 43.1% | 53% / 29% | — |

- **选型定案（2026-11-23）**：微信 `lmcnmac.bin` 与豆包 `sys_bigram`+`sys.dat`
  均已逆向并可离线查询（适配器 `eval/lib/`），但白名单式词对覆盖率仅 16–21%、
  端到端全面弱于万象 → **n-gram 侧固定用万象 LTS**，两家留档不接生产（§11.9）。

- 生产 3-token 打分（安全基线）对整句几乎无效：万象 56% / 41%（B 区噪声级），
  必须用**完整候选 token 的 CE**。
- 整句 CE 成本 ≈ **4ms/候选 token**（0.6B Q4，8 线程；成本 = LM head 行数）：
  回归 `51.0ms + 3.99×Σtoken`，5 候选典型句 **p50 200ms / p95 355ms**
  （3-token 56ms）→ 只能异步、句子输入结束后评分，不能进按键路径。
  插件 DLL 的 `llm.score_full` 已与 3-token 路径**共用同一 context/seq0/prep**
  （2026-11-23 合并，删原独立 `g_full_ctx`）：固定成本 95→51ms（省一次重复的
  ctx forward），§11.7；跨键复用的测量与待办见 §11.8。
